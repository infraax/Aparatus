# M3 — apparatusd: one daemon, one writer

```text
many clients → .apparatus/apparatusd.sock → connection threads → bounded queue → writer actor → FileLedger + CAS
```

M1/M2 stay the source of truth: same kernel, same 11 kinds, same `.apparatus/` files.
M3 wraps them in a process that stays up while clients come and go.

## Run

```bash
apparatus rws init --solo            # once, before the daemon (init never runs beside it)
apparatusd --project .               # foreground; logs to stderr
just daemon .                        # same, restarted by a loop whenever it exits != 0
```

systemd user unit (`~/.config/systemd/user/apparatusd.service`):

```ini
[Service]
ExecStart=%h/.cargo/bin/apparatusd --project %h/projects/demo
Restart=on-failure
[Install]
WantedBy=default.target
```

Stop: `SIGTERM`/`SIGINT` (`systemctl --user stop apparatusd`, Ctrl-C). The daemon finishes queued
requests, removes the socket, exits 0. A client disconnecting never stops it. A crash leaves the
chain intact (append + atomic HEAD); restart on the same project directory resumes.

## How clients find it

- Socket: `<project>/.apparatus/apparatusd.sock`, mode `0600`. No TCP in M3.
- The `apparatus` CLI is daemon-first: if the socket accepts a connection, every `rws` command
  (except `init`, `import-jsonl`) goes over RPC and the CLI takes no lock. Otherwise it runs
  locally under `.apparatus/LOCK`, as in M2. The daemon holds that lock for its whole life,
  so a local writer and the daemon can never write at the same time.
- Stale socket (file exists, nothing listening): the CLI removes it, prints
  `note: removed stale socket …`, and runs locally. `apparatusd` removes it on start.
  A second `apparatusd` on a live socket exits 1.

## Protocol (JSON lines)

One request per line, one response per line, in order per connection.

```json
{"principal":"owner","producer_kind":"human","op":"ingest","content":"text","purpose":"corpus","tag":"C"}
{"status":"ok","ok":true,"id":"…","hash":"…","kind":"ingest","lines":["…"],"error":null,"rule":null,"data":null}
```

- `status`: `ok` | `error` | `refused` (RWS rule, `rule` set, refusal on the chain) | `busy`.
- Reads: `head`, `check`, `show {id}`, `list {what: items|events|tickets}`, `tickets {open}`.
- Writes: `role_bind`, `ingest` (`path` or inline `content`), `queue_keep`, `queue_build`, `gate`,
  `means`, `event`, `advice`, `policy_envelope|policy_agreement|policy_rule`, `correction`,
  `review`, `ticket`, `ticket_close`. Field names match `crates/apparatus-kernel/src/api.rs`.
- Identity: `principal` must already be bound (`role_bind`), else `refused` rule `X-10`.
  `producer_kind`, if sent, must match the binding (`R-08`). No tokens: the socket's file mode is the gate.

## Writer and backpressure

- Every request, read or write, goes through one writer thread that owns the kernel.
- Queue: 64 (`--queue`). Full for 5 s (`--enqueue-timeout-ms`) → `busy`. No answer in 60 s
  (`--reply-timeout-ms`) → `busy` (the write may still land; ask `head`). Never a second writer.
- A panicking handler kills that request only: the writer reloads the chain from disk,
  files a ticket, answers `error`, continues. Invalid JSON → `error`; the next line is served.

## Tickets

A ticket is a `report_back` event (X-12) with a `ticket {title, body, reporter}` field — no new kind.
Closing is a `report_back_resolved` event whose subject is the ticket id (only once: `A-07`).
Unexpected handler errors are filed as tickets under the requesting principal.

```bash
apparatus rws ticket --title "pump does not start" --subject <id> [--body …]
apparatus rws ticket --close <ticket-id> --reason "…"
apparatus rws tickets [--open]
apparatus rws list items|events|tickets
apparatus rws head
```
